# Perf items P5-P18 triage (2026-10-11)

Audit §4 ("Perf improvements, ranked"). Recon from the source, not from
the audit text (which was written against an earlier revision).

| # | Audit claim | Recon verdict |
|---|---|---|
| P5 | Deal-major regret layout + drop atomics in sampled subgame solver | **NOT ACTIONABLE as stated.** The sampled solver already uses `AtomicU64` with per-deal node counters (`nodes_visited: Vec<AtomicU64>`); each deal is single-writer. The layout change (deal-major slabs) would help cache locality but is a large refactor with no measured win. Skip. |
| P6 | Kill heap churn in combinadic unrank (return `[u8; N]`) | **ALREADY DONE.** `combinadic_unrank_2/3/5/6/7` all return `[u8; N]` arrays and sort in place. Only the generic `combinadic_unrank(idx, k, n)` returns `Vec<u8>` and it has no non-test callers. |
| P7 | Vector-solver chance clones -> mask/restore | **TRIED, REVERTED.** Hoisting the reach buffers out of the per-action/per-river loops (3 sites: chance arm, act-traverser arm, act-opponent arm) preserves the golden values (river 0.658723, turn 26.393711 unchanged) but is **measurably SLOWER** -- release median 3778 ms vs 2264 ms on the turn golden (5 runs, 1 warmup). The allocator's per-thread cache is already reusing the freed buffers with better temporal locality than long-lived stack buffers. Not adopted. |
| P8 | RangeTracker posterior loop: cache per-hand hashes within a street | Real (per-action hot path). The hash depends on `(hand, board, history, street)`, and history changes on every action within a street, so caching across actions is not straightforward. Caching per (street, board) prefix is possible but the gain is unmeasured. **Deferred.** |
| P9 | Slim `GameState` ~3.2 KB -> ~2.7 KB (`Action.player: usize -> u8`) | Real. `history: [Action; 48]` at 32 bytes each = 1.5 KB; shrinking `player` to u8 saves ~0.8 KB per GameState, and every clone (which is frequent) becomes cheaper. **But** it touches the on-disk `UndoRecord`, the `Action` public API, and every call site that constructs `Action { player, kind }`. Too risky alongside the current checkpoint set. **Deferred to a dedicated session.** |
| P10 | Signature-gate dispatch -> one `OnceLock<u8>` | Real (three `OnceLock` loads per node visit in `infoset_signature_into`). Small, safe, worth doing. |
| P11 | `TableEvaluator` carries a dead 10.4 MB mmap | **NOT DEAD.** `load_rank_sorted` reads `self.mmap` directly (lookup_fast.rs:149,155); `eval_5_fast` calls it. The mmap is live. Skip. |
| P12 | Stream checkpoints (M-15) + mmap precompute resume | **M-15 DONE** (streaming loader landed). Mmap-on-resume is a separate idea, not measured. Skip. |
| P13 | LBR: share opp-hole+runout samples across candidates (CRN) | Real. Would reduce LBR SE at fixed hands, letting a cheaper LBR be more decisive. But LBR is an offline diagnostic, not a live hot path. **Deferred.** |
| P14 | Zero-mass lane pruning in exact BR | Real (skips hands with zero reach). Win depends on how much of the range is zero-reach at a given node. **Deferred pending profile.** |
| P15 | Parallelize `sample_flop/turn_features` | Real (sequential sample loop) but the sample count default is 200k and the ASSIGNMENT loop (26M entries) is ALREADY parallel. The sampling is likely seconds; the assignment is minutes-to-hours. **Not worth changing.** |
| P16 | Export loop re-pins the map per key | **NOT ACTIONABLE as stated.** `hash_to_idx.pin()` returns a papaya thread-local guard, which is a cheap handle — not a syscall or mutex per call. The guard is re-acquired per `get_average_strategy_into`, but that is by design (the guard cannot be held across the export's other `&self` calls). Skip. |
| P17 | `madvise(MADV_RANDOM)` on the blueprint mmap | **DONE** (commit alongside this doc). The blueprint is random-access; the hint is best-effort. |
| P18 | Lazy mode: skip `term_val` showdown fill; size to fold nodes only | Real but the "lazy mode" already exists (`lazy_term`, `lazy_cache`, `PKR_SUBGAME_LAZY_TERM`). The audit's specific idea (size the array to fold nodes only) is a different memory layout that would need measured justification. **Deferred.** |

## Summary

Of 14 items (P5-P18):
- **Done / already-done:** P6, P12 (via M-15), P17 -> 3
- **Not actionable as stated:** P5, P11, P16 -> 3
- **Not worth the change:** P15 -> 1
- **Small + safe + worth doing:** P10 -> 1
- **Deferred (needs profile or is risk-heavy):** P7, P8, P9, P13, P14, P18 -> 6

## Recommendation

P10 is the last clean win (one `OnceLock<u8>` in the signature dispatch).
After that, the remaining perf items are all either unmeasured or large
enough to need a dedicated session with a benchmark harness. The project
has no `criterion` benches for the runtime hot paths (only contracts,
core, eval, cfr, abstraction); adding one for `get_advice_fast` and
`RangeTracker::apply_action` would let every deferred item be decided
by number instead of by guess. That is the actual next step.
